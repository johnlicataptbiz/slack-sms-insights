Database Schema Refactoring: Monthly Partitioning for sms_events and conversations Tables

Problem Statement

The sms_events and conversations tables in the PostgreSQL database are growing very large, causing query performance to slow down. This impacts dashboard loads and real-time analytics in the PTBiz SMS Insights platform.

Chosen Solution: Option 1 - Monthly Range Partitioning

After evaluating two approaches, we selected native PostgreSQL table partitioning with monthly ranges. This converts sms_events (partitioned by event_ts) and conversations (partitioned by created_at) into partitioned tables. PostgreSQL will automatically route queries to the relevant partitions, improving performance for time-based queries.

Pros and Cons

Pros

  • Massive performance gains for time-range queries (e.g., last 30 days), as Postgres only scans relevant partitions.
  • Easiest way to archive or delete old data (detach/drop partitions).
  • Transparent to application code—no changes needed in queries.

Cons

  • Prisma doesn't natively support partitioning; migrations must use raw SQL.
  • Requires manual setup of partitions and potentially a background process to create new ones.
  • Increased complexity in database management.

Migration Steps

The migration will be implemented as a raw SQL script in a new Prisma migration file. Here's the high-level process:

  1. Create partitioned versions of the tables.
  2. Create initial partitions for existing data (e.g., monthly partitions for the past year).
  3. Migrate existing data to the partitioned tables.
  4. Drop old tables and rename partitioned ones.
  5. Set up a trigger or background job to create future partitions automatically.

Example SQL for sms_events Partitioning

-- Create partitioned table for sms_events
CREATE TABLE sms_events_partitioned (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    slack_team_id TEXT,
    slack_channel_id TEXT,
    slack_message_ts TEXT,
    event_ts TIMESTAMPTZ NOT NULL,
    direction "SmsDirection",
    contact_id TEXT,
    contact_phone TEXT,
    normalized_contact_key TEXT,
    normalized_phone TEXT,
    contact_name TEXT,
    aloware_user TEXT,
    body TEXT,
    line TEXT,
    sequence TEXT,
    sequence_id UUID,
    sequence_version_id UUID,
    event_role TEXT,
    raw JSONB,
    created_at TIMESTAMPTZ DEFAULT now(),
    conversation_id UUID,
    UNIQUE (slack_channel_id, slack_message_ts)
) PARTITION BY RANGE (event_ts);

-- Create example partition for January 2024
CREATE TABLE sms_events_2024_01 PARTITION OF sms_events_partitioned
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- Repeat for other months...

-- Migrate data (assuming existing table is sms_events)
INSERT INTO sms_events_partitioned SELECT * FROM sms_events;

-- Drop old table and rename
DROP TABLE sms_events;
ALTER TABLE sms_events_partitioned RENAME TO sms_events;

-- Recreate indexes (adapted from existing migration)
CREATE INDEX "idx_sms_events_contact_direction_ts" ON "sms_events"("contact_id", "direction", "event_ts" DESC);
-- Add other indexes as needed
